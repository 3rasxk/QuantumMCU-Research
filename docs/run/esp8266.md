# Running the NodeMCU ESP8266 (Phase 2)

**UNVERIFIED — this board has never been run against real hardware in this
project.** Every number below is a prediction from `pc/shared/timing_model.py`
or a compile-only build figure from `docs/preflight_report.md`. Do not
assume the Uno's measured behavior (retry patterns, wall RAM percentage,
warm-up effect) transfers here.

`GPIO_TIMING_PIN = GPIO5` (board silkscreen `D1`,
`firmware/esp8266/src/main.cpp`), logic **3.3V**, UART0 on GPIO1/GPIO3
(never connect a Logic Analyzer there). `--la` is **not implemented** for
this board (Uno Phase 2 only) — passing it is refused by `pc/run.py`.

```bash
.venv/bin/python pc/run.py --board esp8266 --algorithm <circuit> --phase 2 \
    --port /dev/cu.usbserialXXXX
```

`pc/run.py`'s default `--n-max` for this board/phase is **16**
(`pc/phase2_sweep/esp8266_sweep.py`'s own argparse default, line 221).

**`--fresh` changed 2026-09-21** — see `docs/run/uno.md`'s own note and
`README.md`'s "Fresh runs and the archive". The per-circuit minimum-`n`
defaults (`h_all`/`qft`=1, `bell_ghz`/`grover`=2, `qpe`=3,
`steane_encode`=7 fixed) are board-independent, so they apply here
identically — nothing in this table changes because of it, only what `n`
a fresh sweep starts at.

## What to check afterwards

Same file layout and columns as the Uno (`docs/run/uno.md`) —
`data/raw/phase2/esp8266/<circuit>/no_la/{raw.csv,memory_wall.csv,points.csv,sessions.csv}` — always `no_la/` (this board never supports `--la`, see pc/shared/paths.py's no_la/with_la split).
The one ESP8266-specific thing to check: a `watchdog_suspected(...)` status
in `memory_wall.csv` is **not** a Memory Wall — the system distinguishes it
explicitly (`SCHEMA_VERSION 2` onward) precisely because ESP8266's ~8s
hardware watchdog can reset the board mid-repetition on a slow circuit
before it ever gets close to running out of heap. Only `malloc_failed` (the
board self-reporting an allocation failure) or a build-time RAM figure over
100% counts as positive evidence here.

## Known pitfalls (predicted, not yet observed)

- Dynamic allocation (`malloc`) means an out-of-memory condition is
  detected cleanly at runtime (unlike the Uno's silent static-array
  overflow) — but only if the board doesn't watchdog-reset first on an
  expensive circuit.
- Port names follow `/dev/cu.usbserial*` / `/dev/cu.wchusbserial*` /
  `/dev/cu.SLAB_USBtoUART*` depending on the USB-serial chip — unlike the
  Uno, there's no single fixed glob pattern; `pc/run.py`'s port-name sanity
  check only warns (doesn't refuse) if your port doesn't match any of
  these.
- Recommended run order (from `run_checklist.md`, derived for the old
  dataset, not re-verified): Uno, then ESP32, then ESP8266 for the
  `grover` session specifically — cheapest full board banked first.
