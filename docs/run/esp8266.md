## What to check afterwards

Same file layout and columns as the Uno (`docs/run/uno.md`) —
`data/raw/phase2/esp8266/<circuit>/no_ref/{raw.csv,memory_wall.csv,points.csv,sessions.csv}` — `no_ref/` for `--ref none`, `with_ref/` (plus `ref/`) for `--ref counter`.
The one ESP8266-specific thing to check: a `watchdog_suspected(...)` status
in `memory_wall.csv` is **not** a Memory Wall — the system distinguishes it
explicitly (`SCHEMA_VERSION 2` onward) precisely because ESP8266's ~8s
hardware watchdog can reset the board mid-repetition on a slow circuit
before it ever gets close to running out of heap. Only `malloc_failed` (the
board self-reporting an allocation failure) or a build-time RAM figure over
100% counts as positive evidence here.

## Known pitfalls (predicted, not yet observed)

- Dynamic allocation (`malloc`) means an out-of-memory condition is
  detected cleanly at runtime (unlike the Uno's silent static-array
  overflow) — but only if the board doesn't watchdog-reset first on an
  expensive circuit.
- Port names follow `/dev/cu.usbserial*` / `/dev/cu.wchusbserial*` /
  `/dev/cu.SLAB_USBtoUART*` depending on the USB-serial chip — unlike the
  Uno, there's no single fixed glob pattern; `pc/run.py`'s port-name sanity
  check only warns (doesn't refuse) if your port doesn't match any of
  these.
- Recommended run order (from `run_checklist.md`, derived for the old
  dataset, not re-verified): Uno, then ESP32, then ESP8266 for the
  `grover` session specifically — cheapest full board banked first.
