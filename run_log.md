## Standing Operator Decisions (2026-09-20)

Recorded verbatim from the project owner before restarting Uno Phase 2 data
collection from scratch. These decisions govern every Uno session from tag
`pre-run-uno-v2` onward, superseding the ad hoc retry-once-if-timeout policy
used in Session A (tag `pre-run-uno-v1`, discarded — see the "data: remove
uno first-run data" entry below).

1. **Upload failure at some n: re-run that same n, up to 3 attempts total per
   n**, each attempt logged (attempt number, avrdude output signature,
   timestamps, whether the serial port was closed and re-enumerated before
   retrying — see `failure_message` in `data/raw/telemetry/points.csv`, which
   now carries a `[settled ... port_reenum=...]` prefix on any attempt that
   followed a settle). If all 3 fail, log the point as failed and continue
   with the next n — do NOT abandon the circuit. If two consecutive n values
   each fail all 3 attempts, stop the whole run and report (implemented as
   `ConsecutiveUploadFailuresError` in `uno_sweep.py`, exit code 2) — that
   pattern means the failures aren't independent per-point flukes but a
   likely cable/port/hardware problem. Compile errors and link overflow are
   deterministic and are never retried (unchanged).
   **Why:** Session A lost `qft` and `steane_encode` entirely to avrdude
   "not in sync" failures with zero retry, at 11.3%/60.3% compile RAM —
   nowhere near overflow, so not a memory issue.
2. **Memory Wall recorded automatically, no per-point approval needed** — but
   requires *positive evidence*: compile-time RAM > 100%, `build_overflow`,
   or `malloc_failed`. A hang or reset WITHOUT that evidence is NOT a wall (it
   could be a port or watchdog artifact) and is logged as
   `runtime_hang_or_reset` for the owner to review, same as before.
   **Why:** the Uno toolchain's linker exits 0 even when RAM usage is above
   100% (documented quirk, `docs/preflight_report.md` finding L2), so a
   build that "succeeds" per its own exit code can still be a wall — the
   compile_ram_pct check has to run after a successful build too, not only
   inside the existing failure-classification path.
3. **Run ONE algorithm at a time, REPS=100 per point, n from 2 upward until
   the first wall or the circuit's planned n-max. After each algorithm: STOP,
   write the report, and wait for "go" before the next.** Order: `h_all`,
   `bell_ghz`, `qft`, `qpe`, `steane_encode`, `grover`.
4. **All data collected so far on the Uno (pilot + Session A first run) is
   discarded** before collection restarts (see the data-removal entry below;
   preserved in git history at `9c71cfd`, not deleted from the repo's past).
