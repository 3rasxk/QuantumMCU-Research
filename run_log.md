| 2026-09-19 | 100 | Uno/ESP8266/ESP32, all 6 circuits | prep, not yet run | **Resume logic added to all four sweep scripts (`pc/phase2_sweep/{uno,esp32,esp8266}_sweep.py`, `pc/phase3_offload/sweep.py`), plus a duplicate-row guard in both summarize scripts, ahead of the actual REPS=100 run.** Rationale: the full run is estimated at ~11.6h, with single points (ESP8266 grover n=9) running ~3.6h uninterrupted — long enough that the USB-CDC dropout already logged for the n=30 dataset (Uno hung 16+ min on a single `readline()`) is a realistic mid-run failure, and a naive restart before this change would either force re-running a whole board's sweep or silently duplicate rows into the raw CSV, inflating `n_trials` past 100 in the summarize scripts. **Detection:** a point counts as done if it has any row at all in the corresponding terminal-record file (`*_memory_wall.csv` for Phase 2, `*_session_log.csv` for Phase 3) — those files only ever get a row once a point's fate (success, deterministic failure, retry-exhausted failure, or a `skipped_*` decision) is fully resolved, so presence there is unambiguous. Absence means "never tried" or "died before recording an outcome" and either way gets (re)run from scratch. **Orphan rows:** if a process dies between writing raw trial rows and writing the terminal record for the same point, the raw rows survive without a matching terminal entry — resume detects and deletes exactly these rows before the point is redone, so no session ever tops up an existing partial sample to 100 (partial samples span a board reset/reflash/thermal state that isn't comparable to the rest of the 100 trials, so mixing them would misrepresent the variance). **Known-wall inference (Phase 2 only):** if a circuit already hit a genuine wall (`build_or_upload_fail`, `malloc_failed`, or `runtime_hang_or_reset` after its retry policy resolved) at some n in a prior session, resume will not re-attempt any higher n for that circuit, matching the single-session sweep's own behavior of breaking out of the n-loop at the first wall. This inference is deliberately **not** applied in Phase 3: a `session_incomplete` result there is often caused by baud/link instability rather than a deterministic compute limit, and may not recur if the cable or port is fixed before the next attempt. Phase 3's raw/meta write order was also swapped (raw now written before the terminal `session_log` row, matching Phase 2's already-safer order) so the same orphan-detection logic works identically there. Default is resume-on; `--fresh`/`--no-resume` archives the existing CSVs (timestamped rename, never deletes) and starts counting from zero. Verified with synthetic CSVs and mocked hardware I/O (no real hardware touched) — see the corresponding commit for the test cases exercised. | — |

| 2026-09-19 | 100 | Uno/ESP8266/ESP32, all 6 circuits | prep, not yet run | **Per-circuit timeouts replace the flat ones, and two new skip/retry policies apply once this rerun executes.** (1) *Timeout scaling:* `SERIAL_TIMEOUT_S` (Phase 2, was 70s flat) and `SESSION_TIMEOUT_S` (Phase 3, was 300s flat) are gone. Both are now computed per `(circuit, n)` by `pc/shared/timing_model.py` — gate count × per-gate timing constants fitted from the n=30 dataset × safety factor 2.5, clamped to a 90s floor and a 4h ceiling (Phase 3: 300s floor, 2h ceiling). Reason: `grover` at high n costs thousands of times more per data point than `h_all`, so a single flat timeout either misclassifies slow-but-healthy grover points as `runtime_hang_or_reset` (a timeout artifact masquerading as a Memory Wall) or forces every cheap circuit to wait just as long to detect a genuine hang. The budget actually used is recorded per row in `timeout_budget_s` (both `*_raw.csv` and `*_memory_wall.csv`) alongside `expected_point_s`, because "hit a 90s timeout" and "hit a 4h timeout" are not the same finding and cannot be told apart after the fact otherwise. (2) *Retry policy narrowed:* the retry-once-on-transient-failure rule from the 2026-09-16 row now applies **only to points whose timeout budget is ≤ 600s**. Above that the retry is skipped and recorded as `retry_policy=skipped_high_budget`. Reason: a retry's benefit is constant (it rescues one data point) but its cost scales with the budget — worth it at 70s, not worth an extra 4h, especially since the result files are append-only and a single expensive point can simply be re-run on its own afterwards. `retry_policy` is a separate column precisely so these do not blend into the `retry_count=0` rows that mean "succeeded first try". (3) *Compute-infeasible points skipped:* points whose **expected** runtime already exceeds the ceiling are not attempted at all; they are recorded as `status=skipped_compute_infeasible` (Phase 2) / `skipped_sim_cost_infeasible` (Phase 3) with the estimate in `expected_point_s`. This is a genuine finding rather than missing data: `grover` hits a **compute wall below its memory wall** — ESP8266 allocates n=12 comfortably but would need ~95 days per data point. `--force-infeasible` overrides. Every sweep script prints the full budget plan before touching hardware so these are visible up front, not discovered mid-run. | — |
