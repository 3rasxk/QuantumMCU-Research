| 2026-09-19 | 100 | Uno/ESP8266/ESP32, all 6 circuits | prep, not yet run | **Per-circuit timeouts replace the flat ones, and two new skip/retry policies apply once this rerun executes.** (1) *Timeout scaling:* `SERIAL_TIMEOUT_S` (Phase 2, was 70s flat) and `SESSION_TIMEOUT_S` (Phase 3, was 300s flat) are gone. Both are now computed per `(circuit, n)` by `pc/shared/timing_model.py` — gate count × per-gate timing constants fitted from the n=30 dataset × safety factor 2.5, clamped to a 90s floor and a 4h ceiling (Phase 3: 300s floor, 2h ceiling). Reason: `grover` at high n costs thousands of times more per data point than `h_all`, so a single flat timeout either misclassifies slow-but-healthy grover points as `runtime_hang_or_reset` (a timeout artifact masquerading as a Memory Wall) or forces every cheap circuit to wait just as long to detect a genuine hang. The budget actually used is recorded per row in `timeout_budget_s` (both `*_raw.csv` and `*_memory_wall.csv`) alongside `expected_point_s`, because "hit a 90s timeout" and "hit a 4h timeout" are not the same finding and cannot be told apart after the fact otherwise. (2) *Retry policy narrowed:* the retry-once-on-transient-failure rule from the 2026-09-16 row now applies **only to points whose timeout budget is ≤ 600s**. Above that the retry is skipped and recorded as `retry_policy=skipped_high_budget`. Reason: a retry's benefit is constant (it rescues one data point) but its cost scales with the budget — worth it at 70s, not worth an extra 4h, especially since the result files are append-only and a single expensive point can simply be re-run on its own afterwards. `retry_policy` is a separate column precisely so these do not blend into the `retry_count=0` rows that mean "succeeded first try". (3) *Compute-infeasible points skipped:* points whose **expected** runtime already exceeds the ceiling are not attempted at all; they are recorded as `status=skipped_compute_infeasible` (Phase 2) / `skipped_sim_cost_infeasible` (Phase 3) with the estimate in `expected_point_s`. This is a genuine finding rather than missing data: `grover` hits a **compute wall below its memory wall** — ESP8266 allocates n=12 comfortably but would need ~95 days per data point. `--force-infeasible` overrides. Every sweep script prints the full budget plan before touching hardware so these are visible up front, not discovered mid-run. | — |
| 2026-09-16 | 100 | Uno/ESP8266/ESP32, all 3 circuits | prep, not yet run | **Methodology deviation from the n=30 run, applies once this rerun executes:** `pc/phase2_sweep/{uno,esp8266,esp32}_sweep.py` now retry a data point once at the same `n` if it fails with `runtime_hang_or_reset` (hang, serial timeout, or serial read error) — a failure that could be a transient USB/cable glitch rather than a real Memory Wall. `build_or_upload_fail` and `malloc_failed` are still not retried (deterministic outcomes). The n=30 run had no retry logic at all: its first failure at any `n`, of any kind, was immediately the Memory Wall. This means the two datasets' Memory Wall numbers are **not directly comparable** without checking the new `retry_count` column in `*_memory_wall.csv` (also surfaced as `first_failure_after_retry` in `data/processed/phase2/memory_wall_summary.csv`) — a wall that only appears after a retry in the n=100 run might have been recorded as the wall on the very first attempt in the n=30 run, or might not, depending on whether the n=30 failure was itself transient. | — |
